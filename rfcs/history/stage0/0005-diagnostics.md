# RFC-0005: Diagnostics

- Status: Draft (Stage 0)
- Stage-0 build item covered (`docs/plan/15_IMPLEMENTATION_ROADMAP.md`
  Stage 0): "diagnostic schema".
- Owner rulings incorporated: none directly — `project/OWNER_DECISIONS.md`
  D10 (diagnostic code/schema stability policy) remains **open** and is
  explicitly not resolved by this RFC (see §7).
- Depends on: RFC-0002 §3 (kernel-independence constraint on diagnostic
  content).

## 1. Summary

This RFC freezes the diagnostic code taxonomy, JSON schema, and
agent-facing structured-diagnostic contract from
`docs/plan/17_CLI_DIAGNOSTICS_SCHEMA.md` and
`docs/plan/11_AI_NATIVE_SKILLS_AND_AGENT_PROTOCOL.md` §5. Because
`project/OWNER_DECISIONS.md` D10 (whether/how diagnostic codes may be
renumbered pre-1.0, and the process for adding new code families) has not
been ruled on, this RFC freezes the *shape* of diagnostics without freezing
a *stability/versioning policy* for the codes themselves — that remains
open and must not be inferred from this document.

## 2. Diagnostic code taxonomy (frozen, from `17` §10)

```text
PARSE-E###   TYPE-E###     UNIT-E###     RUNTIME-E###   BUDGET-E###
GEOM-E###    TOPO-E###     REF-E###      CONSTRAINT-E### ASM-E###
TEST-E###    REQ-E###      IMPORT-E###   EXPORT-E###    DFM-E/W###
SIM-E/W###   PKG-E###      SEC-E###
```

`E` = error, `W` = warning, `I` = information where needed. This is the
Stage-0 family list; `crates/cad-diagnostics` (AICAD-038) is where a
concrete registry of individual codes within these families begins.

## 3. Diagnostic JSON schema (frozen, from `17` §11)

```json
{
  "code": "REF-E102",
  "severity": "error",
  "category": "reference",
  "title": "AMBIGUOUS_REFERENCE",
  "message": "Reference resolved to 2 faces; expected 1.",
  "source": {
    "file": "src/housing.aicad",
    "start": {"line": 42, "column": 8},
    "end": {"line": 46, "column": 2}
  },
  "entity": "housing.mounting_face",
  "expected": {"count": 1},
  "observed": {"count": 2},
  "candidates": [],
  "suggestions": [],
  "backend_details": null
}
```

(The `"file"` example is updated from the plan's `.cadl` placeholder to the
`.aicad` extension frozen in RFC-0001 §3; no other field changes.)

Every diagnostic surfaced to a human or agent must be an instance of this
schema — a bare string message ("Fillet failed.") is not an acceptable
diagnostic at any layer above the kernel adapter.

## 4. Suggestion-confidence contract (frozen, from `17` §12)

Every entry in a diagnostic's `suggestions` array must be tagged as one of:

```text
machine_applicable   safe, structured patch
likely_fix           supported by deterministic analysis but needs review
informational        conceptual options only
```

An AI agent consuming diagnostics must not treat an `informational`
suggestion as a guaranteed fix, and suggestions must be generated by
reliable geometry/type/reference reasoning — **never fabricated guesses**
(`docs/plan/11_AI_NATIVE_SKILLS_AND_AGENT_PROTOCOL.md` §5). This is a
correctness requirement on whatever code produces a `suggestions` entry,
not merely a UX nicety: a wrong `machine_applicable` suggestion that an
agent applies automatically is worse than no suggestion.

Example, restated from `11` §5 (unit-suffix normalized to this RFC's
conventions):

```json
{
  "code": "GEOM-E204",
  "kind": "FILLET_SELF_INTERSECTION",
  "feature": "housing.outer_fillet",
  "requested_radius": "8mm",
  "estimated_max_feasible_radius": "5.74mm",
  "entities": ["housing.front_vertical", "housing.usb_transition"],
  "suggestions": [
    {"action": "reduce_radius", "max": "5.74mm", "confidence": "machine_applicable"},
    {"action": "use_variable_radius", "confidence": "likely_fix"},
    {"action": "modify_adjacent_geometry", "confidence": "informational"}
  ]
}
```

## 5. Kernel-independence constraint on diagnostic content (cross-reference, RFC-0002 §3)

A diagnostic's top-level `message`, `title`, and `suggestions` must never
require an OCCT-specific concept to be understood. Backend-specific detail
(an OCCT error enum, a native return code) may appear only inside
`backend_details`, and only as supplementary debugging information — never
as the sole explanation of what went wrong or what to do about it. This is
the diagnostics-layer instance of the kernel-independence contract already
frozen in RFC-0002 §3.

## 6. Build/query output schemas and exit codes (frozen, from `17` §13-15)

- Build output carries `status`, `build_id`, `configuration`,
  `changed_features`, `artifacts`, `diagnostics`, `reference_health`,
  `verification`, `resource_usage` (`17` §13).
- Query/entity output surfaces stable semantic information first
  (`semantic_ref`, `entity_type`, `geometry`, `lineage`, `durability` —
  the last matching RFC-0003 §7's durability levels exactly); raw backend
  IDs appear only in a debug section (`17` §14).
- Exit codes: `0` success, `1` build/type/geometry failure, `2`
  test/requirement failure, `3` invalid CLI/project configuration, `4`
  resource/security policy violation, `5` internal compiler/kernel failure
  (`17` §15). Exact numbering may still change before 1.0, but must remain
  documented wherever it changes — this RFC freezes the *meaning* of each
  code slot, consistent with `17` §15's own caveat, not a promise that `1`
  through `5` are permanently immutable integers.

## 7. Open question: diagnostic code/schema stability policy (D10, explicitly not resolved)

This RFC deliberately does **not** answer:

- Whether individual diagnostic codes (e.g. `REF-E102`) may be renumbered
  or removed before a 1.0 release.
- The process for approving a new code family beyond the §2 list.
- Whether the JSON schema in §3 itself may gain/remove required fields
  pre-1.0 without a compatibility note.

`project/OWNER_DECISIONS.md` D10 remains open. `crates/cad-diagnostics`
(AICAD-038), the first task that materializes this schema as running code,
should either wait for a ruling on D10 or treat every code/schema field
introduced before that ruling as provisional and clearly marked as such in
that crate's own documentation — it must not treat this RFC as having
silently settled stability policy.

## 8. Alternatives considered

Since D10 was not ruled on, this RFC's only real choice was *whether* to
freeze the taxonomy/schema/suggestion-contract shape while leaving
stability policy open, versus deferring the entire RFC until D10 is
settled. Deferring the whole RFC was rejected: the code families, JSON
shape, and suggestion-confidence contract in §2-6 are not in dispute
anywhere in the plan or `project/OWNER_DECISIONS.md` (only their
long-term change-management policy is), so freezing the undisputed shape
now unblocks `crates/cad-diagnostics` (Stage 2, AICAD-038) without
requiring a decision that only matters for pre-1.0 stability guarantees.

## 9. Impact

- `crates/cad-diagnostics`: implements §2-4, §6 starting Stage 2
  (AICAD-038); must treat every code as provisional per §7 until D10 is
  ruled on.
- `crates/cad-cli`: implements §6's build/query output schemas and exit
  codes.
- Every crate that raises a diagnostic (effectively all of them, from
  Stage 2 onward) must produce a `17` §11-shaped object, never a bare
  string, and must respect §5's kernel-independence constraint.
- `specs/schemas/diagnostic.schema.json`: to be populated from §3 starting
  Stage 2.
