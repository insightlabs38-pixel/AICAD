# 11 — AI-Native Skills, Tool Protocol, Introspection, and Learnability

## 1. Design target

A capable general-purpose coding model with no prior language training should be able to perform ordinary CAD work after reading **one compact core skill file** and using structured runtime tools.

This is a formal product requirement, not a convenience.

## 2. Skill hierarchy

Recommended official skills:

```text
cad-core.skill.md
cad-geometry.skill.md
cad-engineering.skill.md   (may later split by domain)
```

### Core skill

Loaded for almost all tasks. Teach:

- syntax overview;
- units/types;
- part/sketch/feature basics;
- semantic references and queries;
- assemblies basics;
- build/test/inspect loop;
- common diagnostics;
- package discovery;
- when **not** to use raw topology.

Target: short enough to load routinely.

### Geometry skill

Load only for advanced work:

- curves/surfaces;
- NURBS;
- topology;
- raw handles/epochs;
- healing/sewing;
- complex projection/intersection;
- advanced query/ref recovery;
- unsafe geometry rules.

### Engineering skill

Teach cross-module conventions for:

- drawings/PMI;
- DFM;
- simulation adapters;
- optimization;
- uncertainty/tolerances.

Domain plugins may replace or supplement this.

## 3. Progressive disclosure

Do not stuff the entire API into skill text.

The skill teaches **how to discover**:

```text
cad docs <symbol>
cad search <concept>
cad schema <symbol>
cad package describe <pkg>
cad skill <pkg>
```

The runtime returns exact schemas/signatures/examples on demand.

## 4. Tool protocol

Expose structured, model-friendly tools. Suggested tool names are conceptual; implementation may use MCP or another protocol.

### `cad.build`

Inputs:

```text
project/path
configuration
profile
changed_files? / source_patch?
resource_budget?
```

Returns:

```text
status
build_id
artifacts
structured diagnostics
feature changes
reference health
geometry summary
```

### `cad.test`

Inputs:

```text
project
configuration(s)
test filter
profile
```

Returns test-result objects with expected/observed/entity refs.

### `cad.inspect`

Inputs:

```text
entity/source symbol/project
fields requested
configuration
```

Possible fields:

```text
bounds
mass
volume
topology summary
features
parameters
constraints
references
provenance
dependencies
```

### `cad.query`

Evaluate a semantic/topology query without changing the model.

### `cad.docs`

Exact API documentation and examples for symbols.

### `cad.search`

Search language/installed package concepts.

### `cad.explain`

Deterministic dependency/reference/error explanation; not inherently LLM prose.

### `cad.render`

Generate deterministic viewport renders/selected overlays for visual verification when useful.

### `cad.diff`

Return source + semantic + geometric impact diff.

### `cad.export`

Build and emit STEP/etc. plus fidelity report.

### `cad.packages`

Search installed/registry packages and skills.

## 5. Structured diagnostics for agents

Bad:

```text
Fillet failed.
```

Good:

```json
{
  "code": "GEOM-E204",
  "kind": "FILLET_SELF_INTERSECTION",
  "feature": "housing.outer_fillet",
  "requested_radius": "8mm",
  "estimated_max_feasible_radius": "5.74mm",
  "entities": ["housing.front_vertical", "housing.usb_transition"],
  "suggestions": [
    {"action":"reduce_radius", "max":"5.74mm"},
    {"action":"use_variable_radius"},
    {"action":"modify_adjacent_geometry"}
  ]
}
```

Suggestions must be generated by reliable geometry reasoning, not fabricated guesses.

## 6. Agent loop

Default pattern:

```text
read project instructions
-> load core skill
-> discover relevant packages
-> load package skills only as needed
-> inspect existing design
-> make source patch
-> build
-> fix compiler/geometry errors
-> run tests/requirements
-> inspect relevant geometry
-> render only when visual evidence is needed
-> produce semantic diff
-> stop when requested gates pass
```

## 7. Package skills

Every extension can ship:

```text
ai/skill.md
schema/api.json
examples/
```

Skill responsibilities:

- when to use package;
- concepts;
- preferred abstractions;
- pitfalls;
- required verification;
- links/commands for exact API schemas.

Schema responsibilities:

- exact symbol names;
- parameter types/defaults;
- return values;
- capability requirements;
- deprecations.

Compiler responsibilities:

- enforce correctness.

## 8. Organization/project skills

Support layered instructions:

```text
official core skill
+ organization engineering rules
+ team rules
+ project skill
+ package skills
```

Example project skill:

```text
+Z is up.
Metric only.
Preferred fasteners M3/M5 ISO 4762.
Minimum CNC wall 2.5mm.
Do not modify vendor motor STEP.
Run `cad test --profile release` before completion.
```

## 9. Skill manifest

Recommended package metadata:

```yaml
ai_skill:
  name: robotics.cycloidal
  version: 1.3
  requires:
    - cad-core >= 1.0

  examples: examples/

```

## 10. Learnability benchmark

Maintain a clean "fresh model" benchmark using models that are not fine-tuned on the language.

Test tiers:

### Core only

- mounting plate;
- L bracket;
- enclosure;
- bearing mount;
- patterned flange;
- basic assembly;
- configuration variant;
- fix compiler error;
- fix failing requirement.

### Core + geometry

- spline sweep;
- complex loft;
- surface trim;
- shape healing;
- topology query repair;
- low-level custom feature.

### Package skill

- use unfamiliar third-party package from its skill/schema only.

Metrics:

```text
first-build parse success
compile success
geometric correctness
test pass rate
number of repair iterations
skill tokens loaded
docs/tool calls
raw-topology misuse rate
semantic-reference quality
```

## 11. AI-specific source style

The formatter/linter can optionally encourage patterns that improve agent reliability:

- explicit units;
- semantic naming;
- small functions;
- named arguments for ambiguous geometric calls;
- tests for important generated features;
- avoid raw topology except where needed;
- comments/rationale for non-obvious engineering decisions.

Do not create a separate AI-only language dialect.

## 12. Visual reasoning is supplemental

Agents may render views when:

- interpreting an imported/reconstructed part;
- judging aesthetic/ergonomic shape;
- inspecting a diagnostic where structured geometry is insufficient;
- verifying drawing composition.

But normal dimensional/spatial correctness should come from exact queries and tests, not pixel estimation.

## 13. New feature: model context packets

Provide a compact deterministic context export:

```text
cad context housing --for-agent
```

that includes:

- public parameters;
- semantic refs;
- dependency summary;
- recent failing diagnostics;
- requirement status;
- package APIs actually used;
- bounded geometry summary.

This prevents agents from needing to ingest massive source/assembly state when making localized edits.
