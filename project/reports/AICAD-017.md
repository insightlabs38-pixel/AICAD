# AICAD-017 — Create cad-kernel-api backend-independent handle/error types

## Objective

Populate `crates/cad-kernel-api` with the backend-independent kernel
handle/error type vocabulary its own `README.md` and
`docs/plan/01_SYSTEM_ARCHITECTURE.md` §2.6 already commit it to
(`KernelCurve`, `KernelSurface`, `KernelShape`, `KernelVertex`,
`KernelEdge`, `KernelWire`, `KernelFace`, `KernelShell`, `KernelSolid`,
plus a structured error type), per `project/TASKS.yaml` (AICAD-017).

## Dependencies checked

AICAD-016 (native C ABI boundary) — complete
(`project/reports/AICAD-016.md`). This task's `KernelError` variants are
written to mirror that ABI's `AicadStatus` categories conceptually (see
below), but `cad-kernel-api` itself has **zero** dependency on
`native/occt_bridge` or any FFI crate — converting a raw `AicadStatus`
into a `KernelError` is `cad-occt-bridge`'s job (AICAD-018), not this
crate's.

## What was done

Replaced the AICAD-002/003 placeholder `crates/cad-kernel-api/src/lib.rs`
with:

1. **Nine opaque handle newtypes** (`KernelCurve`, `KernelSurface`,
   `KernelShape`, `KernelVertex`, `KernelEdge`, `KernelWire`, `KernelFace`,
   `KernelShell`, `KernelSolid`) generated by one `kernel_handle!` macro so
   all nine share identical, minimal behavior rather than nine
   hand-duplicated copies. Each wraps a `NonZeroU64` (not a bare `u64`) —
   chosen because `native/occt_bridge`'s ABI (`AICAD-016`) already
   documents `0` as never a valid handle id, so this matches an existing
   invariant rather than inventing a new one, and it gives
   `Option<KernelShape>` (etc.) the same size as the handle itself (a
   claim this task's tests verify directly with `size_of`, not just
   asserted in a comment).
2. **`KernelError`**, a five-variant enum (`NullContext`,
   `InvalidArgument(String)`, `InvalidHandle`, `Internal(String)`,
   `Unknown(String)`) that mirrors `AicadStatus`'s categories
   conceptually — each doc comment cross-references the exact
   `AICAD_STATUS_*` constant it corresponds to — without this crate
   depending on the ABI header or any FFI binding. Implements
   `std::fmt::Display` and `std::error::Error`.
3. **`KernelResult<T>`** — a `Result<T, KernelError>` alias.
4. **`#![forbid(unsafe_code)]`** at the crate root: nothing in this
   crate's scope (opaque newtypes + a plain enum) needs `unsafe`, and
   forbidding it makes that a compiler-enforced fact rather than a
   convention, for a crate whose whole purpose is to be the safe,
   backend-independent vocabulary above the unsafe FFI layer
   (`cad-occt-bridge`/`native/occt_bridge`) that actually needs `unsafe`.

## Implementation decisions (within AGENTS.md's autonomously-allowed
scope; none touch public AICAD language syntax/semantics or the kernel
boundary contract itself)

- **No context-tagging type parameter/lifetime on handles.** A real
  design option to make foreign-context handle misuse a *compile-time*
  error (e.g. a generic `KernelShape<'ctx>` branded lifetime, in the
  style of `GhostCell`/`generativity`) was considered and explicitly
  **not** implemented: `native/occt_bridge`'s handle table already
  rejects foreign-context handles at runtime (verified in
  `project/reports/AICAD-016.md`'s smoke test), Stage 1's kernel policies
  do not require compile-time enforcement, and adding one now would be
  new API-surface complexity with no task evidence yet showing runtime
  rejection is insufficient — exactly the kind of unrequested
  architecture expansion `AGENTS.md` asks this agent to avoid. Documented
  in the crate's module doc so a future task does not have to
  re-discover this reasoning from scratch if the question comes up again.
- **Handle types named exactly as the plan/README already froze them**
  (`KernelShape`, not e.g. `ShapeHandle`) — this task did not choose new
  names; `docs/plan/01_SYSTEM_ARCHITECTURE.md` §2.6 and
  `crates/cad-kernel-api/README.md` (written at AICAD-002/003) already
  commit to this exact list and naming.
- **No `KernelContext` type in this crate.** AICAD-019's own task title
  ("Implement kernel context lifecycle and shape-handle table") makes
  context lifecycle explicitly that task's scope; adding even a minimal
  context type here would risk conflicting with AICAD-019's design before
  it is written.
- **No operation methods on any handle type** (no `.bbox_diagonal()`,
  etc.) — WP-01's "Owns" list assigns curve/surface constructors, B-rep
  operations, etc. to the kernel bridge as a whole, and this task's own
  title scopes it to "handle/error types" specifically; operations lower
  from `cad-geometry-api` (WP-05) through `cad-occt-bridge` (AICAD-018+),
  not from bare handle types in this crate.

## Limitations / follow-up

- Only `KernelShape` currently has a real backend behind it
  (`native/occt_bridge`'s `aicad_create_box`/`aicad_shape_bbox_diagonal`/
  `aicad_shape_release`, AICAD-016). The other eight handle types exist as
  committed API vocabulary (per the plan/README) ahead of the native
  operations that will mint them — expected for an interface crate, not a
  gap in this task; AICAD-018/AICAD-020 onward wire each one up as the
  corresponding native capability is added.
- `KernelError::Internal`/`Unknown` carry a free-text `message: String`
  rather than a further-structured error code, matching
  `native/occt_bridge`'s own current design (a single
  `AICAD_STATUS_KERNEL_INTERNAL_ERROR` for all OCCT-side exceptions, per
  AICAD-016's own recorded limitation) — finer-grained categorization
  should be added together on both sides if a future task's evidence
  shows callers need to distinguish specific backend failure kinds
  programmatically, not spelled out speculatively here.
