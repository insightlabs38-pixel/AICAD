# AICAD-017 — Create cad-kernel-api backend-independent handle/error types

## Objective
Populate `crates/cad-kernel-api` with the backend-independent kernel
handle/error vocabulary named in `docs/plan/01_SYSTEM_ARCHITECTURE.md`
§2.6 (`KernelCurve`, `KernelSurface`, `KernelShape`, `KernelVertex`,
`KernelEdge`, `KernelWire`, `KernelFace`, `KernelShell`, `KernelSolid`)
and RFC-0002 §3 (`project/DECISION_LOG.md#DL-5`), with no FFI or OCCT
dependency — this crate is pure Rust and backend-independent by
construction, not merely by convention.

## Dependencies checked
AICAD-016 (native C ABI boundary) — complete, see
`project/reports/AICAD-016.md`. This task's `KernelId`/`KernelError`
shapes were deliberately designed to mirror
`aicad_shape_handle_t`/`aicad_occt_status_t` from that task's header
one-to-one, so AICAD-018's translation from the native ABI is direct —
but this crate itself does not depend on, include, or reference that
header or OCCT in any way (checked: `crates/cad-kernel-api/Cargo.toml`
has zero dependencies, still).

## What was done

`crates/cad-kernel-api/src/lib.rs`:

1. **`KernelId { context_id: u64, slot: u32, generation: u32 }`** — the
   single backend-independent identity type every handle wraps. Derives
   `Debug, Clone, Copy, PartialEq, Eq, Hash, PartialOrd, Ord` and a
   human-readable `Display`.
2. **Nine distinct handle newtypes** (`KernelVertex`, `KernelEdge`,
   `KernelWire`, `KernelFace`, `KernelShell`, `KernelSolid`,
   `KernelShape`, `KernelCurve`, `KernelSurface`), generated by one
   `kernel_handle!` macro so all nine share identical derives/`Display`/
   `from_id`/`id()`/`From<KernelId>` behavior without hand-duplicating it
   nine times. Each is a distinct nominal type — `KernelFace` and
   `KernelEdge` are not interchangeable at a call site even though both
   are structurally just a `KernelId` — matching the plan's explicit list
   of nine separate names rather than one generic `KernelHandle<Kind>`.
3. **`KernelError`** (`InvalidArgument`, `InvalidHandle`, `StaleHandle`,
   `ForeignContext`, `WrongThread`, `OperationFailed`, `Internal`) — a
   direct one-to-one mirror of `aicad_occt_status_t`'s error variants
   (AICAD-016), with `Display` and `std::error::Error` implemented by
   hand (no `thiserror`/external error-handling dependency added to this
   very-low-in-the-dependency-graph crate).
4. **`KernelResult<T> = Result<T, KernelError>`** convenience alias.
5. A module-level doc comment stating explicitly that these handles are
   build/epoch-local and must never be treated as a durable AICAD
   semantic reference (RFC-0002 §4) — this is the exact distinction
   `project/OWNER_DECISIONS.md` D7/D8 and RFC-0003 depend on staying
   clear as `cad-references` is built in Stage 4.
6. `#![forbid(unsafe_code)]` at the crate root: this crate has no reason
   to ever contain unsafe code (it defines plain data types only), so the
   lint is promoted to a hard compile error rather than left as a style
   preference.
7. Six unit tests (`#[cfg(test)] mod tests`) covering: two different
   handle types constructed from the same `KernelId` remain independently
   correct (documents, via a comment, that a cross-type `==` comparison
   is not just semantically wrong but a compile error — the actual
   type-safety property under test); handles are hashable and behave
   correctly as `HashSet` keys, including deduplication by full identity;
   a stale handle (old generation) and its slot's later occupant (new
   generation) are unequal even though they share a slot number, directly
   testing the property `native/occt_bridge` also asserts on the native
   side; `Display` output for `KernelId` and one handle type, and that
   every `KernelError` variant's `Display` is non-empty; `KernelError`
   satisfies `std::error::Error`; `KernelResult<T>` composes normally in
   `Ok`/`Err` position.

`crates/cad-kernel-api/README.md`: added an "Implementation status"
section describing what is implemented, matching the pattern used in
`native/occt_bridge/README.md` (AICAD-015/016).

## Implementation decisions (autonomous, reversible)
- **One macro generating nine newtypes**, rather than nine hand-written
  structs or one generic `KernelHandle<Kind>` parameterized over a
  zero-sized marker type. The macro keeps the nine types' behavior
  provably identical (same derives, same methods) while still producing
  genuinely distinct nominal types (unlike a generic wrapper, which would
  need a separate marker-type mechanism to get the same non-interchangeability
  property, for no behavioral benefit at this stage). This is a private,
  reversible implementation choice — nothing about it is visible in the
  public type names or their behavior.
- **No external error-handling crate (`thiserror`, `anyhow`, ...).**
  `cad-kernel-api` sits extremely low in the workspace dependency graph
  (essentially every other geometry-facing crate will eventually depend
  on it); keeping it at zero external dependencies avoids forcing a
  dependency-tree choice on every downstream crate for what is, at seven
  variants, a small amount of boilerplate to hand-write.
- **`#![forbid(unsafe_code)]`.** Chosen over `#![deny(unsafe_code)]`
  because nothing in this crate's actual scope (plain handle/error data
  types) should ever need `unsafe`, and `forbid` cannot be locally
  overridden by an `#[allow(unsafe_code)]` later, which is the stronger
  and more appropriate guarantee for a crate whose entire job is being a
  safe, kernel-neutral vocabulary.
- **Variant names mirror the native ABI's status codes exactly** (rather
  than, say, a differently-organized Rust-idiomatic error taxonomy) so
  that AICAD-018's translation is mechanical and reviewable as a direct
  mapping, not a redesign decision made silently inside the FFI wrapper.

## Limitations / follow-up
- This crate intentionally has no constructors that build a `KernelId`
  from raw native ABI values yet (e.g. from an `aicad_shape_handle_t`) —
  that translation belongs to `cad-occt-bridge` (AICAD-018), which will
  depend on this crate and on the native bridge, whereas this crate must
  depend on neither.
- The nine handle types do not yet carry any topology-relationship
  methods (e.g. "get this face's wires") — `cad-kernel-api` owns handle
  *identity* only; operations that traverse/query topology belong to the
  kernel adapter's operation surface (AICAD-018 onward), consistent with
  this crate's README ("must not own source syntax... or AI logic" and,
  by the same logic, must not own operation behavior either).
- Next task: AICAD-018 (create `cad-occt-bridge` safe Rust wrapper),
  which depends on both this crate and the native ABI from AICAD-016.

No escalation condition was triggered: this task defines internal
data-type vocabulary already named by the frozen plan/RFC text (no new
public AICAD language syntax/semantics), does not touch a stage gate or
open `OWNER_DECISIONS.md` item, and does not let any kernel-specific
(OCCT) type leak into this crate — it has no OCCT dependency at all.
